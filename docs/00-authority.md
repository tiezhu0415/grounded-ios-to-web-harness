# 项目 Authority

> 版本：`2026-08-11.1`
>
> 状态：`APPROVED`
>
> 用户批准：2026-08-11，同意 Codex 审查结论并授权限定修正与重新验证。

## 1. 唯一目标

在 1～2 天内跑通一个真实的小型 iOS→Web 功能闭环，用实际结果判断这种 Harness 是否值得继续开发。

## 2. 当前只做

1. 固定并启动一个真实 iOS 项目；
2. 使用成熟工具生成全项目简明蓝图；
3. 由用户选择一个小功能；
4. 详细分析选中功能；
5. 使用 Spec Kit 制订最小计划；
6. 使用 Claude 实现一个 React Web 功能；
7. 使用 Playwright 验证，并由用户最终验收。

## 3. 当前不做

- 不自研 Swift analyzer、AST 或代码知识图；
- 不实现通用 Runner、复杂状态机和数据库；
- 不自动探索或点击所有 iOS 按钮；
- 不要求每阶段 Codex 审查；
- 不要求每阶段价值复盘；
- 不迁移整个 App；
- 不启动第二项目；
- 不增加没有真实需求的 Schema、Gate 和恢复机制。

## 4. 三个决定点

| 决定点 | 条件 | 决定者 |
| --- | --- | --- |
| 源项目可用 | commit 已记录，App 真实启动 | 执行者提供证据 |
| 迁移范围确认 | 蓝图可读，用户选择并确认一个功能 | 用户 |
| 最终验收 | Web 功能和测试结果可查看 | 用户 |

## 5. 角色

| 角色 | 职责 |
| --- | --- |
| 用户 | 选择功能、批准方向、最终验收 |
| Claude | 主执行者，维护计划、分析、实现和测试 |
| Codex | 用户按需触发的只读审查者；默认不参与每个步骤 |
| Harness | Skill、少量脚本、模板和证据目录的组合 |

## 6. 审查和循环限制

- Claude 自动修复同一问题最多两轮；
- Codex 只在用户要求、最终验收前或连续两轮修复失败时调用；
- 出现第三轮同类问题时必须停止并向用户报告；
- 聊天决定只有写入本文或用户文档后，才成为长期项目事实。

## 7. 批准后的第一步

当前 eCommerce MVP 实现已完成，Codex 首轮审查结论为 `ADJUST`。修正已进入 `FIXED — AWAITING REVALIDATION`，最终验收仍由用户决定。

## 8. 通用性边界

- Harness 的通用部分是五阶段工作方法、配置入口、planning/handoff 规则和证据要求；
- `xcode/eCommerce-main`、`webapp/` 及当前中文蓝图/验收报告是首个验证示例，不是 Harness 固定业务能力；
- 新项目必须通过自己的 `harness.yaml` 提供路径、project、scheme、模拟器和 Web 输出目录；
- `harness.example.yaml` 不得包含 eCommerce、商品或本机路径；
- 当前通用性只达到 `SMOKE_VERIFIED — ONE PROJECT`，尚未通过第二项目，不能宣称已经证明跨项目通用。
